# 判定在推理机内完成，中心不在实时路径上

三值判定、SOP 实例边界与安全不变量都在推理机的扩展 checker 内实现。中心是管理面与聚合面：下发配置、接收上报、提供看板与复核。中心不订阅推理服务 SSE，不做判定。

## 两条独立理由

**一、有效性所需的第一手信号在推理机。** 区分"没做"与"没看到"需要流健康，而流健康信号产生于 DeepStream pipeline 的 `on_message` 回调（`ds_3d_action_pipeline.py:780-790`）。该回调当前只处理 EOS，把 source error、正在重连、重连成功、最后一帧时刻、恢复后时间轴归零全部丢弃，从未进入 SSE。把判定放在中心，中心就只能靠独立 RTSP 探活二次猜测同一件事——那是两套互相不一致的实现，而正确答案在推理机。改造 `on_message` 输出这些事件、让同机的 checker 消费，是唯一不产生重复实现的路径。

**二、中心不得是实时防错的单点故障。** 原设计把订阅与判定放在中心的单一 ingest 进程（`replicas=1`），中心一挂，全部工位同时失去实时防错，而物理联锁信号还要绕中心跑一趟。工厂产线不接受这种拓扑。判定与处置在推理机本地闭环后，中心离线只影响看板与复核。

## Considered Options

- **中心 ingest 订阅 SSE + 中心 judgment 模块**（原方案）：模块边界干净，但同时踩上面两条——第一手信号拿不到，且中心成为全厂单点。
- **中心判定 + 边缘探活上报健康**：把流健康从推理机传到中心再判定。信号绕一圈，延迟与失真都增加，且中心单点问题不变。
- **判定进推理机（采纳）**：判定与信号源、与处置执行点同机。代价是判定代码运行在基座容器的 Python 环境里。

## Consequences

- 流租约不再需要。租约存在的唯一理由是"中心多个进程可能重复订阅同一路相机、重复启 DeepStream pipeline 重复占显存"。本机 supervisor 驱动本机 pipeline 后，"每路流有且仅有一个拥有者"退化为本机进程管理问题。原 ADR-0001 因此作废并删除。
- 判定核心只能依赖 Python 标准库：它运行在 DeepStream 容器内，Python 版本由基座镜像决定，用不了中心的 uv 工作区。这条约束同时保证判定核心可纯 CPU 单元测试——基座那四个模块本来就只依赖标准库。
- 中心的 `monitor` 模块是上报镜像而非判定权威，行覆盖来自推理机的幂等 upsert。判定权威、违规锁存权威与处置执行权威都在推理机本地 SQLite。
- 推理机需要本地持久化、对账协议与版本握手。这是消除单点故障的必要成本。
- 每台推理机都要能独立排障。诊断日志与指标必须在本机可读，不能只在中心聚合后才可见。
