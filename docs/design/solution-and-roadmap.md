## 一、产品定位与硬约束

把工厂标准作业转成机器可执行的模板，在现场实时回答：当前在做什么、是否合规、偏离后留什么证据、触发什么响应。

**【已定】基座是本产品的躯干，不是外部依赖。** NVIDIA 仓库已实现的能力原样复用；接近但不够的就地改造；基座完全没有的才新建。不允许出现"基座有一套、我们再写一套"的重复实现——这条约束优先于"`vendor/` 只读"这类洁癖，见 §5.11 与 [ADR-0007](../adr/0007-base-is-the-trunk-not-a-dependency.md)。

**【已定】交付的必须是真实可用的系统，不允许任何 mock / 模拟实现。首要价值是实时防错。**

**【已定】推理机是自治判定单元；中心不可达时现场继续工作。** 每台推理机独立完成取流、感知、判定、违规锁存、处置（含写输出点位）与证据缓冲，本地持有模板版本、设备配置与凭据。中心是管理面与聚合面，不在实时判定路径上。中心离线时推理机按最后确认的模板版本继续判定与处置，本地排队，恢复后对账；处置不重复执行，证据不丢失。见 [ADR-0005](../adr/0005-judgment-runs-inside-the-inference-host.md)。

**【已定】性能优先。每个成功实时结果的端到端延迟目标为 ≤ 500 ms。** 该目标按结果类型分两个起点（§5.6）：**到达即判类**（错步、反序、超时、顺序型模板的跳号漏步）起点是形成该结果所需的最后一帧在相机侧产生；**闭合类**（实例闭合时的集合比对）起点是闭合条件成立时刻。终点同为对应状态或判定完成 Web 渲染。目标环境门禁要求测试窗口内超预算结果为零，同时报告 p50/p95/p99、最大值、超预算计数、队列深度与积压趋势；未在目标 GPU、相机、网络和浏览器上通过前，不把该目标表述为已实现能力。

**【已定】优先对齐推理服务公开契约，不为传输层另造体系。** 视频帧留在推理机；DeepStream/PyServiceMaker 形成 chunk，经 VLM 与 checker 判定后由本机上报中心。REST/JSON 负责配置、查询和命令；中心向 Web 推送 SSE。关键路径不增加 Kafka、gRPC、自定义 WebSocket 或数据库轮询，除非 profiling 证明必要。

## 二、实测事实（方案的地基）

### 2.1 基座判定层分不清"没做"与"没看到"

基座 `nvds_action_detector` 的 `__init__.py`、`ds_logger.py`、`missing_number_detector.py`、`sop_step_checker.py` **只依赖标准库**，本机纯 CPU 可直接运行。同一份 5 步 `actions.json`，输入动作序列 `[1,2,4,5]`：

| 场景 | 基座输出 |
|---|---|
| 真漏步（操作员跳过第 3 步） | `missing=[3]` |
| 断流（第 3 步期间视频中断） | `missing=[3]` |

**输出完全相同**。基座无任何通道区分二者，且 checker 请求里根本没有流健康字段 → 三值判定（通过 / 不通过 / 不可判定）必须由我们补进 checker（§5.2）。

### 2.2 基座的周期边界启发式会把合规作业误判为违规

这是本方案最关键的一条实测。5 步 SOP，操作员做 1,2,3 后**返工重做 2**，再继续 4,5——一遍完全合规的作业：

```
输入(1)  missing=[]        输入(2)  missing=[]        输入(3)  missing=[]
输入(2)  missing=[4,5]  ← 返工触发周期边界，误报漏步
输入(4)  missing=[]        输入(5)  missing=[]
终帧     final_missing=[1,3]  ← 再误报一次
```

一遍合规作业被判了两次不合规。根因在 `missing_number_detector.py:149-166`：见重复号且已见 `N×0.6` 个动作即认定新周期开始，`seen_in_cycle` 被清空；或低号 ≤`N×0.3` 出现在高号 ≥`N×0.8` 之后同样触发。返工在工厂是常态，该启发式在产线上不可用。

→ **`MissingNumberDetector` 不是状态机，是靠两条启发式猜周期边界的有状态序列校验器。** 序列比对逻辑可用且应复用；**周期边界必须换成模板声明的信号**（§5.1、[ADR-0006](../adr/0006-cycle-boundary-is-declared-not-inferred.md)）。

### 2.3 基座对漏步的报出时机达不到实时

逐 chunk 模拟真实流式（漏第 3 步的一遍作业）：

```
chunk1 动作(1)  cycle_completed=False  missing=[]
chunk2 动作(2)  cycle_completed=False  missing=[]
chunk3 动作(4)  cycle_completed=False  missing=[]
chunk4 动作(5)  cycle_completed=False  missing=[]
```

作业已结束，基座完全沉默。根因在 `process_number`：`cycle_completed=True` 的条件是 `len(seen_in_cycle) == N`，漏一步永远凑不满。`missing` 只在两个时机产出：

1. 下一遍作业开始时触发周期边界（实测 `[1,2,4,5,1,2,3,4,5]` → 第二遍开始才吐 `missing=[3]`）；
2. 流结束（`keep_alive=False`，SSE 终帧）→ 吐 `final_missing=[3]`。

对 7×24 常驻流，时机 2 永不发生 → **当班最后一遍的漏步永远不报**。声明式边界 + 空闲时限在源头消除这个缺陷（§5.1）。

### 2.4 流健康信号存在于 pipeline，但被丢弃

复核 `69352021` 后修正早期"无重连"结论：RTSP pipeline 给 `nvurisrcbin` 设置了 `init-rtsp-reconnect-interval=10`（`ds_3d_action_pipeline.py:477-494`）。按 NVIDIA DeepStream 源码，该属性在 RTSP 源收到错误时等待后触发重连；基座没有设置用于"持续无数据"检测的 `rtsp-reconnect-interval`，也没有显式设置重连次数。

关键在于 `ds_boundary_infernce` 的 `on_message` 回调（`ds_3d_action_pipeline.py:780-790`）**只处理 EOS**：source error、正在重连、重连成功、最后一帧时刻、恢复后时间轴归零全部被丢弃，从未进入 SSE。`checker_result.error_message` 也只反映 checker 自身异常。

→ 流健康的第一手信号就在推理机的 pipeline 回调里。**判定必须与它同机**，否则中心侧只能靠独立探活二次猜测——那正是"两套东西"。改造方案见 §5.7。完整证据见 [`nvidia-base-capability-boundary.md`](../research/nvidia-base-capability-boundary.md)。

### 2.5 基座三项能力空白

- **无时间概念**：`deadlineMs`、超时、时限一概不存在，`time.time()` 只测性能。超时违规须由我们从 chunk 的 `start_time`/`end_time` 与主机单调钟自己算。
- **无处置动作**：对外响应面只有 Kafka 发消息（`messager.py`）与 `playsound` 播告警音。
- **无 ROI / 外部信号 / 目标检测。**

### 2.6 检查器阈值在部署态不可配（实测）

`ChatCompletionRequest`（`api_types.py:245`）**没有** SOP 检查阈值字段；`ds_sop_process.py:675` 硬编码 `0.6/0.3/0.8`，:735 从 chunk dict 读同名键，而**全仓无任何代码往 chunk 写这三个键**（已 grep 确认）。`SopDetectionOptions` 只用于内部 checker 服务，不在公开契约上。

→ 部署态阈值恒为默认值，且无环境变量可改。这三个阈值只服务于将被替换掉的边界启发式（§2.2），换成声明式边界后它们不再有意义。模板版本的运行参数只含产品侧可调参数（空闲时限、超时时限、处置策略）；**顺序性声明不是运行参数**，见 §5.3。

### 2.7 DDM 权重不随仓库提供，但可自训

`triton_model_repo/ddm/1/model.py` 里写死：

```
"DDM checkpoint not found at {...}. A fresh box has no checkpoint until you
fine-tune/download one. Obtain a DDM-Net checkpoint (e.g. via the SOP Training
Blueprint), place it under MODEL_ROOT_DIR, and set DDM_MODEL_PATH..."
```

`api_server.main()` 在非 DUMMY 模式下调 `wait_for_model_ready()` → **没有 DDM 权重，服务起不来**。

训练程序支持单 GPU 配置：`ddm_train_config.yaml` 为 `num_gpus: 1`、`resnet50`、`resolution: 224`、`frames_per_side: 5`、`batch_size: 4`、`epochs: 10`、`amp: false`。这不等于已证明单张 4090 的峰值显存、训练时长或准确率；须按目标环境验证矩阵实测。

**DDM 标注格式**（实测 `ddm_dataset.py:330-395`）：

```json
{ "<video_id>": [ {"start_timestamp": 0.0, "end_timestamp": 6.67, "description": "..."}, ... ] }
```

整段视频需在 `data_root/{video_id}.mp4`；边界 = 相邻片段 `end_timestamp` 与 `start_timestamp` 的中点 × fps；描述含 "final segment" 的片段被过滤。

**本地样本数据可转换**（实测）：`server_fan/raw/` 有 12 个整段视频，`server_fan/train/Install_N/` 是切好的片段。以 Install_8 为例：raw 视频时长 71.54s，11 个片段时长合计 71.54s，差值 **0.00s（0.0%）**——片段是整段视频的完整无重叠切分。

**⚠️ 实现期必须实测的坑**：文件名格式 `{序号}_{视频}_{周期}_{动作号}.mp4`，序号 `10` 出现两次（`10_Install_8_1_1.mp4` 与 `10_Install_8_2_11.mp4`，后者周期=2）→ **按文件名排序 ≠ 时间顺序**。定序难题移交给标注环节的人（§5.4）。

样本数据自带的 `train/actions.json` 与 `augmented/{gqas,bcq,mcq,golden_gqa}` 是 **VLM 微调格式**，不是 DDM 格式。

### 2.8 视频链路成本（本机 10 核实测）

| 操作 | 单路 | 8 路并发 |
|---|---|---|
| CPU 解码（1280×592/29fps） | 0.42s / 23.24s 视频 = **55× 实时** | 2.58s / 186s = **72× 实时** |
| CPU 解码 + 缩放 224 | 37× 实时 | — |
| NVDEC 硬解（GTX 960） | 1.48s = 16× 实时 | — |
| **x264enc 转码**（1080p，推理服务 `SW_ENCODER` 确切参数 `superfast zerolatency bframes=0`） | 3.92s / 20s = **5.1× 实时**，占 ~0.2 核 | 14.96s / 160s，跟得上但吃 **~10 核** |
| **零转码 passthrough** | 0.17s = **121× 实时** | 0.21s = **773× 总吞吐** |

→ 解码取流不是瓶颈；**转码才是**。8 路软编吃 10 核，50 路需 ~60 核，不可行。

### 2.9 推理服务预览/录像路径都碰 GPU

- RTSP 输出分支：`SW_ENCODER=true`（compose 默认）走 `x264enc`（CPU 编码），`false` 走 `nvv4l2h264enc`（GPU NVENC）；两者均 `bframes=0`。但**前置必经 `nvvideoconvert`（带 `gpu-id`）**，占 GPU 显存与转换算力；且与判定支路共享 pipeline，有反压风险。
- `ENCODE_VIDEO`：对**每个 chunk 无条件编码**，无违规过滤；`encode_video_gst` 内部**写死 `nvv4l2h264enc`**，`SW_ENCODER` 管不到 → 7×24 持续 GPU 编码 + 磁盘无上限增长。

→ 两条都不能用于生产预览/证据。预览与录像走独立的 mediamtx 路径（§5.5）。

### 2.10 基座其他既定事实

- **API**：OpenAI 兼容，11 端点（`docs/openapi.json` 随仓库提交）：`POST /v1/chat/completions`（SSE，`chunk_metadata` 携带 checker 结果）、`/v1/files` CRUD、`/v1/models`、`/v1/metadata`、`/v1/live`、`/v1/startup`、`/v1/ready`、`/v1/metrics`。输入三形态：`video_url`、`input_video`(file_id)、`input_camera`(Basler)。分段：`ddm-net` 或 `uniform`（后者绕过 DDM）。
- **chunk 可用字段**：`chunk_idx`、`start_time`、`end_time`、`cv_boundary_score`、`cv_execute_time`、`first_timestamp`、`pipeline_starting_timestamp`、`pipeline_cv_ready_timestamp`、`checker_result`。
- **模板与 prompt 是进程级配置**（实测）：`ACTION_CONFIG_PATH` 在 `ds_sop_process.py:113` 于模块加载时读入，每个 `SOPVideoProcessor._initialize_checker()`（:662）从同一路径读同一份文件；API 请求无模板 id 字段。→ **一个推理服务进程只承载一份 SOP 模板**，这直接决定部署形态（§5.10）。
- **镜像**：`nvcr.io/nvidia/blueprint/vss-engine:2.4.1`（NGC 门禁）+ `deepstream:9.0-triton-multiarch` + 商业 Basler Pylon SDK。容器内 Python 版本由 DeepStream 9.0 基础镜像决定，不由我们选择（§5.11 的依赖约束由此而来）。
- **安全**：官方明写无 AuthN/AuthZ、明文 HTTP、单租户、无速率/并发限制。
- **训练侧**：5 个微服务（标注 8100、增强 5487、CR 微调 32080、DDM 微调 32100、评估 32090）+ **自带 `metadata_db`（Postgres）与 Adminer 8080**；Cosmos 全量微调官方参考 `4 × A100 80GB`。
- **agentic/**：三个 Claude 插件包（`ds-sop-skills`、`sop-agentic-ft` 6 个 skill、`vss-sop-skills`），随 subtree 进仓库即可用。

### 2.11 mediamtx 选型依据

不做重编码（瓶颈在带宽非 CPU）；支持 `sourceOnDemand` / `runOnDemand`（仅在有客户端请求时拉源流）；内置分段录像 + 保留策略 + 回放服务 + 快照提取；**WebRTC 不支持 B 帧**。

海康子码流是否无 B 帧**未经查证**（详细编码规格需登录官方文档），只查到"低码率、延迟稳定"。此项列为拿到真机首验项（§5.5），不作为已知事实使用。

### 2.12 piko `authoring_worker` 是空壳

三个文件共 130 字节，`__main__.py` 导入的子模块不存在 → `ModuleNotFoundError`，README 声称的 `--check` 跑不起来。无可复用代码。

## 五、关键机制设计

### 5.1 SOP 实例边界：声明式，替换基座启发式

**问题**：基座的周期边界靠两条启发式猜（§2.2），返工即误报；且漏步只在下一周期或流结束才报（§2.3）。

**方案**：保留 `MissingNumberDetector` 的序列比对逻辑，**替换其边界来源**。边界由模板声明的信号决定，不由代码分支决定，也不由动作序列形状猜。判定层只消费归一化观测，不知道某条观测来自动作识别还是某个外部连接器。

- **开实例**：模板声明的开始信号首次满足。
- **闭实例**（三者任一先到）：
  1. 模板声明的结束信号满足；
  2. 动作集合齐全（`len(seen) == N`，基座已有的 `cycle_completed` 快路径，保留）；
  3. **空闲超时**——最后一条观测到达后超过模板声明的"工位空闲时限"仍无新观测。
- **闭合前强制过有效性门**（§5.2）：查该路流健康与推理可达性，任一不健康则闭合为不可判定，**不得进入漏步集合比对**。

**空闲时限必须用推理机主机单调钟度量，不能用 chunk 时间戳。** chunk 时间戳无法度量"chunk 不再到达"。这一点关系到安全不变量：断流后 chunk 停止到达 → 计时器触发 → 若直接算漏步就会输出不通过，正是 §2.1 教训的复现。上一道有效性门就是为拦住这条路径而存在。

**顺序型模板的漏步提前报出**：模板声明步骤严格有序时，下一动作到达且跳号即判漏步，闭合时的集合比对退为兜底。基座已有 per-action 的 `actions_can_be_skipped` 概念，可表达"该步可跳过"。不做这件事，"实时防错"对漏步就兑现不了——而漏步是四类违规里最常见的。

**返工不再误报**：边界不再由重复号触发，`seen_in_cycle` 不会在实例中途被清空。§2.2 的用例固化为回归测试（§5.9）。

可声明为开始/结束信号的来源，取决于该工位配了什么：

| 信号源 | 前提 |
|---|---|
| 动作编号（VLM 输出） | 无（所有工位可用） |
| 外部信号（已配置的连接器点位，语义如"工件到位"） | 该工位配了对应连接器 |

**单通道感知的固有局限**（记入 [ADR-0009](../adr/0009-single-channel-perception-limit.md)）：仅以动作编号为开始信号时，操作员漏做**起始动作**则实例开不了，该遍作业完全不被记录（而非误判违规）。这不是实现缺陷。若某工位对此不可接受，可为其配置一个外部信号作为开始信号——"工件到位"是物理事实、不依赖动作识别。这是**部署期的配置选择**，不是产品架构前提：没配的工位走同一套代码路径，只是可声明的信号源少一个。

### 5.2 三值判定与 14 个原因码

**安全不变量（必须在代码中显式成立）**：

```
if 证据覆盖不足 or 流不健康 or 推理不健康 or 时间未对齐:
    判定结果 != 不通过
```

判定与该不变量都在推理机的判定核心内实现（[ADR-0005](../adr/0005-judgment-runs-inside-the-inference-host.md)），因为有效性所需的第一手信号在本机 pipeline 回调里（§2.4）。

不可判定原因码（10）：`STREAM_LOST`、`INFERENCE_BACKEND_UNREACHABLE`、`INFERENCE_TIMEOUT`、`TIMESTAMP_DISCONTINUITY`、`CHUNK_BACKLOG_EXCEEDED`、`ACTION_ID_UNKNOWN`（VLM 输出动作号不在模板声明内）、`INFERENCE_HOST_DOWN`、`RUN_INTERRUPTED`（配置切换中止 / 进程重启）、`IO_SIGNAL_LOST`（模板依赖的输入点位不可达）、`IO_TIME_UNALIGNED`（外部信号与视频时间轴对齐偏差超阈值，§5.8）。

不通过原因码（4）：`MISSED_STEP`、`WRONG_STEP`、`OUT_OF_ORDER`、`DEADLINE_EXCEEDED`。

每个原因码在界面映射一句人类可读的排障提示。不引入第四态"降级判定"——VLM 不可用但流健康时直接不可判定 + `INFERENCE_BACKEND_UNREACHABLE`；第四态会让现场语义复杂化而收益有限。

**三值与违规锁存的关系**：违规一经确认即锁存，与所属实例的最终判定结果相互独立。实例可以是"不可判定"而同时挂有一条已锁存的违规——前者说"这一遍整体结论不可靠"，后者说"这个偏离是已被确认的事实"。两者都上报，界面分别呈现。

### 5.3 Excel → 模板版本 → 推理机的生成链路

```
平台 Excel（工位表 + 步骤表，保留原文件与导入记录）
  → 解析校验（步骤号连续、工位号存在、必填完整、编码规范）
  → 平台内模板草稿（可编辑的权威记录）
  → Studio 修改步骤、声明步骤顺序性、补运行参数（空闲时限、超时时限、处置策略）
  → AI 生成提示词措辞 + 步骤对齐（调推理服务核对边界）[Q25 待确认]
  → 由持模板编辑权限的用户发布
  → 不可变模板版本（actions.json + vlm_prompts.txt + 运行参数 + sha256）
  → 推理机按绑定拉取并落到本地，重启该后端进程生效
  → 推理机上报实际生效版本的 sha256（reported_version）
```

**`actions.json` 格式必须严配基座正则 `^\((\d+)\).+`**——`sop_step_checker` 用它提动作号，不匹配则 checker 静默失败。

**运行参数与顺序性声明是两类不同的东西，在 `template_version` 中是两个字段。** 运行参数是产品侧可调值（空闲时限、超时时限、处置策略），改它不改判定逻辑的形状；**顺序性声明是模板语义属性**——它决定步骤是否严格有序，从而决定跳号是否即判漏步（§5.1），改它改变判定逻辑本身。基座那三个阈值（0.6/0.3/0.8）在部署态不可配（§2.6），且只服务于被替换掉的边界启发式，二者都不属于，故不进模板版本。

**权威边界**：Excel 是可追溯的导入来源；解析成功后，平台内模板草稿是步骤和运行参数的权威记录。重新上传 Excel 创建新的导入/草稿，不静默覆盖已有草稿。

**下发是拉取式**：推理机主动向中心拉取自己绑定的模板版本，中心不推。中心不可达时使用本地已缓存的最后一个已确认版本继续运行（§5.7）。

### 5.4 首切片控制面与 Web 基线

首切片只交付可操作控制面，不显示虚构运行状态：

- **模板**：导入规范化 SOP 文档、编辑模板草稿、发布、生成/校验/下载 `actions.json`、VLM prompt、运行参数和 sha256。
- **身份与权限**：本地账户；系统管理员、设备管理员、模板编辑者、数据集管理者、运行操作员、复核人员。角色是权限集合，一个用户可拥有多个角色；LDAP/OIDC 后置。
- **工位与设备**：工位唯一编码/名称/标签；相机、推理后端和连接器支持持久化 CRUD、关联约束。允许离线保存；"测试连接"执行真实请求，结果为成功、失败或未验证，不返回模拟成功。
- **Web**：简体中文；桌面 Chrome/Edge 当前稳定版；1366×768～1920×1080；键盘可操作、表单有标签和明确错误、颜色不是唯一状态表达。导航为概览、工位与设备、SOP 模板、训练数据集、用户与权限；概览只显示真实配置摘要。
- **明确后置**：实时运行看板、违规处置、证据复核、大屏、统计报表、整改闭环、原生移动端和企业身份源。

#### 训练数据集与标注

**【已定】只允许上传视频，不接受压缩包，后端不解压。** 训练素材以单个视频文件逐个上传；视频是本产品拥有的客户资产，其归属、权限与生命周期归 `dataset`。随之作废的有：tar 成员安全校验、`dataset_member` 的"压缩包成员"语义、以及从已切片段反推 DDM 时间戳的转换器。

- **正式入口**：Web 与脚本调用同一应用 API 上传视频，不直接写数据库。上传经预签名 URL **直传 MinIO**，控制面只负责签发、登记与校验。预签名 URL 按 `dataset.dataset.import` 权限签发并限时。
- **`dataset` 拥有**：视频登记（来源、大小、sha256、时长、编码）、数据集分组、用途检查状态、派生制品引用。
- **动作时间段标注：原样复用基座 React 标注 UI。** 基座 `video-annotator-ms`（React + FastAPI）已实现时间轴标注、切片与训练触发。它经 Nginx 反代进统一入口，鉴权在网关补齐；**不用 Vue 重写**——那正是"两套东西"（§5.11、Q34）。标注是产生 DDM 所需 `{video_id: segments[]}` 的唯一途径。
- **一个必须知道的代价**：本地样本包内已有的切片（`server_fan/train/Install_N/`）与 VLM 微调数据（`augmented/`）不再能整体带入。片段本身是 mp4 可上传，但 DDM 需要"整段视频 + 各片段时间戳"，时间戳只能由标注产生。§2.7 的定序难题**移交给标注环节的人**。
- **VLM 用途检查**：校验 GQA/BCQ/MCQ/Golden GQA 结构、视频引用、动作编号及与当前基座提交的数据契约；通过后只标记"可用于后续微调"。首切片不启动 VLM 或 DDM 训练。

### 5.5 预览与录像（与 GPU 完全无关）

**海康 RTSP 地址格式**（已查证）：

```
主码流（判定用）: rtsp://<user>:<pass>@<ip>:554/Streaming/Channels/101
子码流（预览用）: rtsp://<user>:<pass>@<ip>:554/Streaming/Channels/102
```

注意事项（已查证）：密码含特殊字符必须 URL 编码（`@`→`%40`、`:`→`%3A`）；经 NVR 接入时通道号由 NVR 分配、不是 1；子码流特性是低码率、延迟稳定。

**⚠️ 拿到真机后必须首验**：子码流实际编码与 profile（`ffprobe` 看 `has_b_frames`）。WebRTC 不支持 B 帧（§2.11）——若子码流带 B 帧，先按具体型号能力尝试在摄像机 Web 配置中调整 codec/profile/GOP；**能关闭不兼容编码是零转码方案成立的前提**。配不掉才对该路启 x264enc 转码并在界面标注额外 CPU 开销。

```
相机主码流(101) ──→ 推理机推理服务容器（判定，GPU）
相机子码流(102) ──→ mediamtx（sourceOnDemand，零转码）
                     ├─→ WebRTC 单路详看（浏览器直连）
                     ├─→ WebRTC 多路大屏（浏览器直连，容量须实测）
                     └─→ 分段录像（保留 7 天）→ 违规时 ffmpeg -c copy 切片 → 上传中心 MinIO
```

排除推理服务 DeepStream RTSP 输出与 `ENCODE_VIDEO`（§2.9）。

**录像磁盘容量**：`子码流码率 × 路数 × 7 天 × 1.3`。余量系数覆盖 VBR 峰值、文件系统开销与"不跑满盘"三项，**算例必须含它**。按 1 Mbps 估算（1 Mbps × 604800 s = 75.6 GB 裸容量，×1.3 后）：

| 路数 | 裸容量 | 含余量（按此备料） |
|---|---|---|
| 1 | 75.6 GB | **~98 GB** |
| 8 | 605 GB | **~786 GB** |
| 50 | 3.78 TB | **~4.9 TB** |

这是推理机的硬件清单项，须在 C4 门禁前按实际码率复算。子码流实际码率高于 1 Mbps 时按比例放大。

### 5.6 500 ms 的两个起点

同一个 500 ms 数字，按结果类型分两个起点——不拆则门禁由构造即失败（闭合类判定的"最后必要源帧"可能在空闲时限之前）：

| 结果类型 | 起点 | 涵盖 |
|---|---|---|
| **到达即判** | 形成该结果所需的最后一帧在相机侧产生 | 错步、反序、超时、顺序型模板的跳号漏步、实时状态更新 |
| **闭合类** | 闭合条件成立时刻 | 实例闭合时的集合比对结论 |

终点同为对应状态或判定完成 Web 渲染。闭合后只剩序列比对 + 写本地状态 + 上报 + 推送，500 ms 是合理预算。两类分别报告 p50/p95/p99、最大值与超预算计数。

判定在推理机本地完成，因此"判定产生"到"处置执行"不跨网络；跨网络的只有上报与 Web 推送。中心不可达时判定与处置照常，Web 看板停止更新——**看板延迟不属于实时防错的功能路径**。

### 5.7 推理机是自治判定单元

每台推理机上的组件：

```
推理服务容器（基座 + §5.11 两处改造 + 我们的判定核心）
  DeepStream 取流 → DDM 分段(Triton) → vLLM 分类 → 判定核心（序列比对+边界+有效性+三值）
  pipeline on_message → 流健康事件 → chunk_metadata → 判定核心
本机 supervisor（自研）
  读本地配置，为每路已配置相机启动一个 /v1/chat/completions 请求并看护
  违规锁存 / 处置派发（含写输出点位）/ 证据切片指令 / 上报与对账
mediamtx（sourceOnDemand，零转码，7 天分段录像）
连接器运行时（轮询或推送输入点位 → 观测；执行输出点位写入）
本地状态存储（SQLite）
```

**为什么流租约不再需要**：租约（原 ADR-0001）存在的唯一理由是"中心多个进程可能重复订阅同一路相机，重复启 DeepStream pipeline 重复占显存"。判定回到推理机后，是本机 supervisor 驱动本机 pipeline，不存在跨机竞争者；"每路流有且仅有一个拥有者"退化为本机的进程管理问题。ADR-0001 因此作废。

**本地状态存储用 SQLite**：嵌入式、单机、标准库自带，不给推理机再加一个数据库服务。存本地配置缓存、已确认模板版本、在飞与已闭合实例、判定、已锁存违规、处置记录、待上报队列、待上传证据队列。

**中心不可达时的行为**：

| 能力 | 中心离线时 |
|---|---|
| 取流、感知、判定 | 继续（不受租约约束） |
| 违规锁存 | 继续 |
| 处置：记录 / 前端告警 / 声光 / 暂停工位判定 / 终止实例 | 继续 |
| 处置：**写输出点位** | 继续，直至物理执行租约过期（TTL 7 天，§5.17）；过期后降级并显式标注 |
| 证据切片 | 继续，本地缓冲排队 |
| 预览（浏览器直连 mediamtx） | 继续 |
| 模板版本变更、工位改绑 | 不生效，继续用最后已确认版本与归属 |
| 上报、看板、复核 | 暂停，恢复后对账 |

**对账语义**：上报按事件 id 幂等 upsert，至少一次；处置记录带幂等键，恢复后不重复执行已执行的动作；证据上传失败可重试且不删除本地唯一副本。版本握手在连接时进行，不兼容即显式告警并拒绝接入，不静默降级（[ADR-0003](../adr/0003-api-v1-is-a-fixed-prefix.md)）。

**健康状态的两种语义与写入者**（避免 `device` 与 `monitor` 各存一份"健康"）：

| 字段 | 语义 | 写入者 |
|---|---|---|
| `device_inference_host.健康状态` | 主机级**可达性**：中心能否连上这台机、上次上报距今多久 | 中心（心跳与上报时距，见下条自指问题） |
| `device_inference_backend.健康状态` | 进程级**可达性与就绪**：`/v1/live`、`/v1/ready` 的最近结果 | 中心（轮询基座健康端点） |
| `device_connector.健康状态` | 设备级**可达性**：最近一次测试连接或轮询结果 | 推理机上报（连接器运行时在本机，§5.8） |
| `monitor_stream_health` | **每路观测有效性**：连接/重连/断开时间线与时间锚定偏移，是三值判定的依据 | 推理机上报（源自 pipeline 回调，§2.4） |

前三者是"能不能连上"，`monitor_stream_health` 是"这段时间的观测能不能用于判定"。**判定只看后者**；前三者服务于运维界面与告警。看板把它们并排显示由适配层组合，不新建聚合模块。

**推理机自评健康的自指问题**：§5.2 不变量的四个条件全部由被评估的那台推理机自己产生。若该机部分子系统失能（磁盘满导致 `local_report_queue` 写入失败、supervisor 卡死）而判定输入链路表面正常，它仍会输出不通过，本机没有任何信号能发现这件事。故需要一个**不依赖被评估者自述的外部证人**：中心以"该机多久没上报"为独立判据，超阈值即在看板标注该机全部工位为可疑并告警。这不违反"中心不做二次探活"（ADR-0005）——中心判的不是流健康，是**这台机还活着吗**，二者信号来源与用途都不同。

### 5.8 连接器

连接器是**可配置集成点**，与相机、推理后端同级：能配、能不配、配了就用。判定逻辑不因某工位有无某类连接器而改变代码路径——这条是硬约束，代码中出现 `if 配了连接器: ... else: ...` 即为违反。

**连接器运行时在推理机内**，与判定同进程域：外部信号必须与动作编号并列进判定，物理联锁必须在本地闭环——停线信号绕中心跑一趟既加延迟又加故障点。配置由中心的 `device` 拥有并被推理机缓存；输出写入由本机 supervisor 的处置派发发起。

**时间对齐是配置了输入点位后的强制要求**：

| 观测来源 | 时间基准 |
|---|---|
| 动作编号（chunk） | `start_time`/`end_time` = 相对流开始的秒数 |
| 外部信号 | 主机时钟的绝对时刻 |

偏移不可用或漂移超阈值时，依赖外部信号的判定输出不可判定 + `IO_TIME_UNALIGNED`，**不得输出不通过**。这是 §5.2 安全不变量在这一维度的落地。

**适配器与真硬件开发路径**（避开 mock）：海康摄像机自带告警输入/输出接线端子，ISAPI 暴露以下端点（已查证存在）：

```
/ISAPI/System/IO/inputs/<ID>          读写告警输入口配置
/ISAPI/System/IO/inputs/<ID>/status   读告警输入状态
/ISAPI/System/IO/outputs/<ID>/status  读告警输出状态
```

第一个适配器写海康 ISAPI，用真设备验证整条链路。板卡到货后只增加第二个适配器，上层不动。

**各适配器的能力边界要在设备管理页显式呈现**：摄像机告警口通常只有 1~2 路输入 + 1 路输出，继电器负载约 1A / DC30V。够接光电开关、按钮、指示灯，**不够做产线联锁**——停线联锁须用工控机板卡或经认证的 PLC/安全回路。

**待实测**：ISAPI 请求体格式；**是否有 `alertStream` 类推送端点**——这条决定外部信号是推送还是轮询。若只能轮询，轮询周期直接构成时间对齐误差下限，会限制外部信号能承担的判定类型。

**默认取舍**：外部信号**不作为违规的唯一证据**——单点位信号无法区分"没按"与"线路故障"，与 §2.1 的教训同构。

### 5.10 推理后端 = 一份模板配置的进程端点

**【已定】** `actions.json` 与 VLM prompt 是进程级配置（§2.10 实测），故**一个推理服务进程只承载一份 SOP 模板**。据此定义：

**推理后端是"承载一份模板配置的推理服务进程端点"，不是"一台推理机"。** 一台推理机可运行多个推理后端；共用同一后端的相机必须共用同一模板。

选这个模型而不是"一机一模板"，是因为它把后者当特例包住：若实测容不下多容器，退化为"一机一后端"只是部署约束，不改表结构；反之若先定"一机一模板"，将来要 per 工位模板就得改 `device` 与 `monitor` 两个模块的表。

三个连带后果：

- vLLM 是独立端点、可被多个后端共享；每个后端的额外常驻开销是一份 DDM Triton 实例 + CUDA context。**该开销须在 G2 门禁单列**，它是容量公式的一项。
- G4 门禁改测「N 后端 × 1 路」，原「1 后端 × N 路」测不到真实部署形态。
- `device_camera` → `device_inference_backend` 外键语义随之明确：指向进程端点，不指向物理机。物理机由 `device_inference_host` 表达。

### 5.11 基座姿态：两处改造 + 一处自己实现

**语言前提**：NVIDIA 仓库的代码是**本系统的躯干**。文档中不称"上游"，只在描述 `git subtree pull` 的版本来源时称 **NVIDIA 仓库**。

**【已定】分类清单**（[ADR-0007](../adr/0007-base-is-the-trunk-not-a-dependency.md)）：

| 姿态 | 范围 |
|---|---|
| **原样复用** | DeepStream 取流、DDM 分段、vLLM 分类、`/v1/*` 接口、文件 API、Prometheus 指标；训练侧 5 个微服务；**React 标注 UI 连界面一起复用** |
| **就地改造（两处，纯加输出）** | ① pipeline `on_message`：把 source error / 正在重连 / 重连成功 / 最后一帧时刻 / 时间轴归零输出到 `chunk_metadata`；② 处置：把 `playsound` + Kafka 扩成 5 种动作含写输出点位 |
| **自己实现（一处）** | 序列比对 + 声明式边界 + 有效性门 + 三值判定，全部在 `apps/edge-runtime/`，`vendor/` 不留补丁 |
| **全新建设** | 账户权限、工位/相机/连接器配置、Excel→模板版本发布、聚合看板、违规复核、证据生命周期、上报与对账 |

两处就地改造都是在回调/派发点**追加调用**，不进入他人控制流，故"最小 hook 在 `vendor/`、逻辑在 `apps/edge-runtime/`"这一分工成立；不动 DeepStream/Triton/vLLM 的计算路径，NVIDIA 的性能改进与 CUDA 版本适配仍可 `subtree pull` 进来。

**为什么序列比对不打补丁**：`missing_number_detector.py` 中周期边界判断（`:147-188`）与序列比对、状态更新交织在 `process_number` 同一方法内——`_complete_cycle()` 调用、`seen_in_cycle` 清空、`result` 填充全在其中。换边界来源必须整体覆写该方法，"最小 hook"对它做不到。该文件全文 539 行、只依赖标准库，自己实现比在他人状态机内解冲突更省。

这不违反"不许两套实现"：我们的判定路径上只有一套（我们的），基座那份在该路径上不再被调用。

**代码放置**：`apps/edge-runtime/` 是独立 Python 包，在容器内安装；`vendor/` 内只留两处最小 hook。我们的代码因此可被 lint、type check 与单元测试覆盖。补丁维护为可重放 diff，`subtree pull` 后由契约测试验证仍可干净应用。

**依赖约束（硬规则）**：判定核心只依赖 Python 标准库。原因是它运行在 DeepStream 容器的 Python 环境里（版本由基座镜像决定，§2.10），用不了我们自己的 uv 工作区；且这条规则保证判定核心可纯 CPU 测试——基座那四个模块本来就是这样。

被否决的两种姿态：**全量只读**会让中心再建一套判定与探活，而第一手信号在推理机（§2.4），必然产生两套不一致的实现；**全量吸收**低估 GPU 基础设施维护成本，等于自建一个 DeepStream 维护团队。

### 5.12 凭据在推理机本地

**凭据在推理机本地录入、本地加密存储、本地校验。** 中心只存"该相机凭据已配置/未配置"的状态标志，不存密文也不代管（[ADR-0008](../adr/0008-credentials-stay-on-the-inference-host.md)）。

理由：中心一旦代管凭据，推理机重启就依赖中心可达——与 §一 的自治约束直接冲突。中心也就自然满足"不提供明文读取接口"，因为它从来没有过密文。

- 中心生成的推理机配置骨架**不含秘密**，只有占位符与说明。
- 推理机本地密钥由部署时挂载的只读 secret 文件提供，不进入 Git、日志、API 响应或导出。
- 凭据写入后只能覆盖或用于本机真实连接测试，不提供明文读取接口。
- 诊断日志只记录操作人、目标、时间和结果，不记录秘密值。

### 5.13 模型权威在推理机

**推理机部署 vLLM，型号可自定义，推理机是模型的权威。** 中心通过基座已有的 `/v1/metadata` 与 `/v1/models` 读取该机实际加载的模型标识，写入判定溯源。不建中心模型注册表模块，不做中心分发。

代价须说明：判定溯源里的模型版本从"中心保证的绑定"降级为"推理机自报的事实"。对内网单工厂交付够用；若将来要求"某工位必须用某个 checkpoint 才能判合规"，再加一致性校验。DDM checkpoint、VLM 权重的许可闭包与离线可分发性仍是 L1/L2 门禁项，由部署流程而非中心模块承担。

### 5.14 异步任务用 ARQ，不立独立 Worker 进程

piko 立独立 Worker 进程的三条前提在本项目**全部不成立**：后台本身就是 Python/FastAPI（无语言边界）；GPU 被推理机独占，中心不做 GPU 工作；中心读不到推理机显存压力，做不到限速/暂停。

但**异步长任务需求是真的**：步骤对齐要调推理跑多遍模板视频，十分钟级；训练编排更长。Excel 解析反而是亚秒级，不需异步。

→ 用 **ARQ 任务队列**（Redis 已在栈内，原生 async、依赖轻）。

**【已定】投递语义：PostgreSQL 为权威，Redis 只作传输**（[ADR-0004](../adr/0004-postgres-is-the-job-authority.md)）。`job` 模块拥有 `job_application_job` 表；入队走事务性 outbox（与业务变更同事务写 job 行，提交后投递 Redis），worker 按 job id 幂等执行，语义为至少一次。不得直接调用 `arq.enqueue` 绕过 outbox。**补投由 ARQ cron 任务扫表完成，不新增进程。**

ARQ 只处理导入校验、制品生成等后台任务，不进入实时判定链路——实时链路整体在推理机内。

### 5.15 控制面契约基线

以下为前后端共同起步所需的最小契约，是**跨模块统一纪律**，不是逐资源的实现细节。

**资源身份**：对外身份是服务端生成的 UUIDv7。自然键（工位编码、登录名）保留唯一约束，作为查询过滤与导入匹配键，**不作为 URL 身份**。

**错误契约**：RFC 9457 `application/problem+json`，扩展成员 `error_code`（稳定 SCREAMING_SNAKE 枚举）与 `field_errors[]`。**`error_code` 与 `reason_code` 是两个不同类型**：前者是 API 调用失败的原因，后者是判定结果的领域理由（§5.2 的 14 个）。二者在 OpenAPI 中是两个枚举，禁止共用字段名——混用会让"不可判定"被前端当成 HTTP 失败处理。

**授权**：权限决策归 `auth`。**`authorize` 调用点在各模块的 `usecases/` 层**（用例边界），不在 HTTP 路由——ARQ worker、上报入口与 smoke 脚本调用同一批用例，只在路由强制等于让权限依赖调用方自觉。路由上的权限声明是元数据（供 OpenAPI 展示），由机械检查保证「每个写路由都声明了权限且与用例实际检查一致」。权限命名固定三段 `module.resource.action`，在代码中是枚举而非裸字符串；粒度为 `view` / `edit` / `delete`。

**不做审计事件**：不建独立审计表。变更归属由各实体的 `created_by` / `updated_by` / 发布者列承担；操作痕迹由诊断日志承担。这是明确取舍：放弃"业务事实与业务变更同事务、不可丢、append-only"的强度，换取模块与运维面更简单。若商业交付要求合规审计，需重新引入并承担相应改造。

**诊断日志**：structlog JSON 输出，五个必填字段 `event` / `module` / `correlation_id` / `level` / `ts`。**`event` 是稳定 snake_case 标识符**（如 `template.version.publish.rejected`），检索靠它而非文案。禁止裸 `print` 与 `logging`，由 ruff 规则保证。不建事件名注册表。日志配置与 correlation id 传播属共享基础设施（`factory_sop/observability/`），被所有模块 import，自己不 import 任何领域模块，由 `import-linter` 保证；**它不是一个领域模块**——不拥有表，也不拥有领域行为。

**并发写**：模板草稿等可被多人编辑的记录带整型 `revision`，写请求携带 `If-Match`，不匹配返回 409 + `error_code=STALE_REVISION`。理由：静默丢一条步骤的后果是"已发布模板少一步"，而漏步正是本系统要检出的违规类型。

**停用与删除**：可变配置对象（工位、相机、推理后端、连接器、用户）用**停用**表达下线，可逆，历史记录与关联关系完整保留；**删除**是另一项按权限开放的操作。模板版本不适用停用——它是不可变记录，回滚即重新绑定历史版本。停用用户必须同时吊销其全部会话。

**长任务进度**：REST 轮询 `GET /api/v1/jobs/{id}`。看板 SSE 在运行切片随上报入口一起落地。

**推迟的契约（显式清单，非沉默省略）**：推理机→中心的上报契约（`ReportedDecision`、`ReportedViolation`、`ReportedHealth`）与中心→推理机的拉取契约（`TemplateBundle`、`DeviceConfigBundle`）留到运行切片，用真实录制 chunk 与真机行为确定。seam 的名称、拥有模块与落表位置已在 §六/§七 固定。`packages/contracts/` 首切片只放导出的 `openapi.json`。理由：ADR-0003 的兼容性门禁为保护真实调用方而设——把未见过真实数据的猜测放进去只会锁死自己。

**通用约定**：时间戳全部 UTC RFC3339（`Z`），Web 按 Asia/Shanghai 渲染；枚举在线格式为稳定 snake_case 字符串，不用数字；列表统一信封 `{items, page, page_size, total}`。

**验收场景**：以场景表（ID + 前置 + 动作 + 可观察结果）形式随各实施切片给出，`tests/system/` 用同一 ID 命名测试，使"哪条验收未实现"可 grep。不引入 Gherkin 层。

### 5.16 模块形状与切片顺序

**【已定】`api.py` 是跨模块契约，不是本模块的对外入口全集。** 每模块有一个用例层（`usecases/`），授权在此强制；`api.py` 只暴露**其他模块真正调用的那个子集**。例如 `device` 的约 40 个配置用例中，只有 `resolve_station_topology`、`report_health` 这类会被 `template`/`monitor` 调用的进 `api.py`，其余停在用例层。

理由：`api.py` 的存在理由是限制跨模块耦合面。把只有 HTTP 一个调用者的用例也塞进去，会让"跨模块契约"与"对外 API 全集"混成一个文件，`import-linter` 也就无法再告诉我们哪些行为真的被别人依赖。反过来，若让配置类模块的 CRUD 一律穿过 `api.py`，得到的是 HTTP handler → `api.py` → repository → 表，中间那层不贡献任何东西。

**【已定】首切片纵向推进，两个例外先落地。** `auth`（所有切片的授权都依赖它）与基座契约测试（纯 CPU 无依赖）先做；之后按 `device` → `template` → `dataset` 逐个端到端（表 + 迁移 + 用例 + API + 前端页）完成再下一个。

理由：横向分层会让第一个可演示的东西出现在整个首切片末尾，而多处待实测项（海康子码流 `has_b_frames`、ISAPI 有无推送端点、标注定序）只有走到那一层才会暴露。代价是迁移历史更碎，但单一线性历史 + 文件名前缀（§六）使这代价可承受。

**【已定】判定核心在首切片实现，作为 `apps/edge-runtime/` 的纯函数模块。** 输入是自己拥有的 Python 类型，无 HTTP 入口、无表、无生产者。

理由：§5.2 的安全不变量与 §5.1 的边界逻辑是整个产品最高风险的部分，而它们完全不需要 GPU 或真实数据就能测（§2.1、§2.2 已实测）。推到运行切片等于让最危险的逻辑与最难调试的环境（GPU + 真实流 + 时序）同时首次出现。§2.2 的返工用例就是首切片第一个要通过的测试。**代价：首切片存在一个不可从 Web 到达的模块**，这要在切片验收里写明，不得被当成"未完成"。

**【已定】前端按导航项划分五个模块**（概览、工位与设备、SOP 模板、训练数据集、用户与权限），不按后端模块划分。**概览的跨模块聚合由 HTTP 适配层组合**：各模块用例层各出一个 `summary()`，适配层在同一请求级 UoW 内调用并组装响应。

理由：新建 `overview` 模块会拥有一份不属于自己的数据视图，是典型的表形状模块；让某个现有模块跨界读表直接违反所有权规则；前端并发调四个接口则把"什么构成概览"的业务定义泄漏到浏览器。适配层做纯组合（不含判断逻辑）本就是它的职责，且 ADR-0002 已让它持有请求级 UoW。

**标注 UI 是例外**：基座 React 标注 UI 原样复用，经 Nginx 反代，不纳入 Vue 五模块划分。

### 5.17 工位改绑与物理执行权

判定回到推理机后，"每路流有且仅有一个拥有者"退化为本机进程管理问题（§5.7）。但**"哪台推理机有权驱动这个工位的执行器"不因此消失**——它是跨机问题，且后果比重复占显存严重得多。

失效场景：工位 A 原绑推理机 1，凭据、模板、连接器点位全在机 1 本地生效。运维在中心把工位 A 改绑到机 2，但机 1 未被物理下线（网络故障或运维遗漏）。因"中心不推、推理机拉"（§5.3），中心无法通知机 1 交权；机 1 靠本地缓存继续判定与处置，两台自治单元同时对同一停线联锁点位发指令。

**【已定】握手为主、租约为辅。**

- **改绑握手**：中心侧改绑操作**默认阻塞**，直到旧推理机确认已停止该工位的判定与处置并释放点位。旧机在下次拉取配置时看到"该工位已转出"，停止该路 pipeline、释放连接器点位、上报交权确认；中心收到确认后才允许新机接管。
- **强制改绑**：旧机永久失联（硬件损毁、报废）时提供强制通道，**需二人确认**（操作者 + 另一名持设备管理权限的用户），显式警示"若旧机仍在运行将造成重复物理写入"，并产生诊断日志事件记录两名确认人。这是全系统唯一要求双人的操作——因为它是唯一可能同时驱动两套物理执行器的操作。
- **物理执行租约（兜底）**：写输出点位需持未过期租约，租约在每次成功拉取配置时续期，**TTL 为 7 天**。过期后该机降级为"只判定、只上报、不写点位"，界面显式标注该工位物理防错已失效。

**为什么 TTL 取 7 天而不是 24 小时**：TTL 短会拿例行风险换失误风险。中心周五晚故障、周一才修是例行情况，24h TTL 会让所有推理机在周末无人值守时段静默失去物理防错能力；而"改绑却不下线"是操作失误，已由握手与双人确认拦住。租约只负责"旧机永久消失且未走强制通道"这一残余情形，7 天足够运维发现。

**判定与上报不受租约约束**，可无限期靠本地缓存继续——只读行为不会造成物理冲突，而这正是自治的价值所在（§一）。

## 六、系统结构

**【已定】技术与部署基线**：中心后台采用 FastAPI + SQLAlchemy 2.x + Alembic；基础 Web 采用 Vue 3 + TypeScript + Vite，并通过 OpenAPI 生成客户端。Nginx 是统一访问入口。Nginx、FastAPI、ARQ worker、PostgreSQL、MinIO、Redis 与原样复用的训练微服务由一份中心机 Compose 统一安装和运维。Web 登录使用 `HttpOnly + Secure + SameSite` 会话 Cookie，修改请求执行 CSRF 校验，不在 `localStorage` 保存长期令牌。

中心后台是**模块化单体**：业务模块在一个 FastAPI 部署单元内通过进程内接口协作，各自拥有行为、表和迁移；首版不引入内部 HTTP、服务网格、消息总线或分布式事务。

首切片持久化只启用 PostgreSQL、MinIO 与 Redis；TimescaleDB 在 `monitor` 开始持久化时序上报时的实施切片中再启用。推理机本地状态用 SQLite（§5.7）。

**【已定】统一访问入口是控制面入口，不是全流量中继。** Nginx 只承载 Web 静态资源、中心后台 REST/JSON、会话、小数据实时更新，以及原样复用的标注 UI 与训练微服务（在网关补鉴权）。视频的 WebRTC 信令与媒体均由浏览器直连推理机 mediamtx。

```
中心机（管理面，非运行面）                推理机 A（自治判定单元）      推理机 B
├── Nginx 统一访问入口                   ├── 推理服务容器             ├── 推理服务容器
│    ├── Vue3 前端                       │    DeepStream→DDM→vLLM     │
│    ├── /api/v1 → FastAPI               │    →判定核心（我们的）      │
│    └── 反代：标注 UI / 训练微服务       ├── supervisor（锁存/处置/    ├── supervisor
├── FastAPI 后台（单一入口点）            │    上报/对账/证据切片）      │
├── PostgreSQL（+Timescale 后置）         ├── 连接器运行时              ├── 连接器运行时
├── Redis / MinIO / ARQ worker           ├── mediamtx                 ├── mediamtx
└── 训练微服务（原样复用）+ metadata_db   └── SQLite 本地状态          └── SQLite
                                               ↑                          ↑
          ← 上报（幂等 upsert）                相机 1~8                  相机 9~16
          → 拉取（模板/配置，推理机主动）  （视频不跨中心；中心离线现场继续判定与处置）
```

**中心后台模块**（8 个）：

| 模块 | 拥有 |
|---|---|
| `auth` | 用户、角色、权限、会话 |
| `device` | 推理主机、工位、相机、推理后端、连接器配置、凭据配置状态标志、健康聚合 |
| `template` | Excel 导入/校验/配置生成/版本/发布/绑定/desired-reported 对账 |
| `dataset` | 训练数据集登记、用途检查、派生制品引用 |
| `monitor` | 推理机上报的镜像：SOP 实例、判定、流健康；看板状态 |
| `alert` | 违规归档、处置记录归档 |
| `evidence` | 证据引用与人工复核 |
| `job` | 异步任务权威与投递（outbox；ADR-0004） |

诊断日志与 correlation id 传播不是模块，是共享基础设施（§5.15）。

**中心不再有的东西**：`judgment` 模块（判定移入推理机的判定核心）、`runtime` 的 ingest 进程（不再订阅 SSE）、流租约表（ADR-0001 作废，§5.7；但工位物理执行权仍需管，见 §5.17）。中心的 `monitor` 是**上报镜像**，不是判定权威——它的行覆盖来自推理机的幂等 upsert。

`dataset` 是独立模块而非 `template` 的一部分：`CONTEXT.md` 对「训练数据集」的定义明确写了它不定义 SOP 模板，并把「SOP 模板」列为 _Avoid_ 项，合并二者会在代码层重新粘合术语层刻意拆开的概念。

**推理机侧组成**（`apps/edge-runtime/`）：判定核心（纯标准库、纯函数）、边界求解、本地状态（SQLite）、supervisor（请求看护 / 锁存 / 处置派发 / 上报对账）、连接器运行时、mediamtx 看护、证据切片。`vendor/` 内只留最小 hook 调用本包（§5.11）。

**依赖规则**：判定核心不依赖任何相机 SDK、推理框架或连接器实现，只消费归一化观测；中心各模块各自拥有数据表，不跨模块直接读写；前端只调后端用例，不承载判定规则。

**【已定】边界靠机械检查，不靠评审。** 每个中心模块一个 Python 包，包内 `api.py` 是唯一允许的跨模块导入目标；`import-linter` 契约在合并门禁中强制：判定核心不得导入任何适配器包、任意模块只能导入他人 `api`、`adapters/*` 不得被 domain 层导入。物理表名带模块前缀（§七），使迁移所有权可纯静态判断。

**【已定】跨模块用例共享一个请求级事务**（[ADR-0002](../adr/0002-request-scoped-unit-of-work.md)）：HTTP 适配层开启并提交单个 Unit of Work，模块门面只参与、不自行提交，`Session` 经请求作用域注入。代价是事务边界不再兜底模块边界，故上述机械检查是本决定的前提而非可选增强。

**【已定】迁移为单一线性 Alembic 历史**，单一 `versions/` 目录，文件名前缀标注所属模块（`0007_template_...`）；合并门禁检查一个迁移文件只触及其前缀模块拥有的表。

**【已定】工作区与工具链**：中心后台 Python 锚定 3.12，`.python-version` 与 `uv.lock` 提交，CI `uv sync --frozen`；根一份 `pyproject.toml` + uv workspace。lint/type 用 ruff + mypy strict。**`apps/edge-runtime/` 的判定核心只依赖标准库**（§5.11 硬规则），因其运行在 DeepStream 容器的 Python 环境中，版本不由我们选择。Web 侧 pnpm workspace 在 `control-web` 落地时创建。

**【已定】配置与秘密**：`pydantic-settings` 单一 `Settings`，环境变量为唯一来源，秘密经 `*_FILE` 路径变量读文件而非读值；启动强制校验无默认弱值，缺失即拒启，不降级为不加密。推理机本地凭据同规则（§5.12）。

**【已定】会话与口令**：会话记录由 `auth` 存于 PostgreSQL（重启不掉线，可强制下线），口令用 Argon2id。不用无状态签名 Cookie——无法即时吊销。

**【已定】基础 Web 栈内选型**：Element Plus + Pinia；OpenAPI 生成的 TS 客户端置于 `apps/control-web/src/api/generated` 并提交，CI 校验重新生成后工作区干净。`packages/` 需两个真实调用方才允许上移。

**【已定】API 前缀**：控制面路径固定 `/api/v1`，但该前缀不是版本轴，不会出现 v2（[ADR-0003](../adr/0003-api-v1-is-a-fixed-prefix.md)）。`openapi.json` 由 FastAPI 生成并导出到 `packages/contracts/`；契约检查必须让删除路径/字段、新增必填字段、收窄类型失败。推理机是可能非同步升级的客户端，靠启动时版本握手而非 URL 版本。

**契约清单**：**推理服务 OpenAI 兼容 API**（基座既定，我们是同机消费者）、**上报契约**（推理机→中心：`ReportedDecision` / `ReportedViolation` / `ReportedHealth`）、**拉取契约**（中心→推理机：`TemplateBundle` / `DeviceConfigBundle`）。后两者字段留到运行切片按真实数据确定（§5.15）。

实时结果路径固定为：

```text
相机主码流 → DeepStream → chunk → DDM → vLLM → 判定核心（序列比对+边界+有效性+三值）
            → 本机 supervisor：违规锁存 / 处置执行（含写输出点位）/ 证据切片
            → 上报中心 → 中心 SSE → Web 看板
```

判定与处置在虚线以上全程不跨机。中心 SSE 只服务看板，不在防错功能路径上。REST 不轮询替代该流。

## 七、数据模型要点

物理表名带拥有模块前缀，使迁移所有权检查可纯静态判断，且 grep 一个前缀即得该模块全部持久化面。

### 中心（PostgreSQL）

- **配置域**（`device`）：`device_inference_host`（物理推理机：主机标识、网络地址、mediamtx 地址、健康状态、时钟偏移）、`device_inference_backend`（**一份模板配置的进程端点**：外键 → host、base_url、承载的模板绑定、健康状态）、`device_station`（含空闲时限）、`device_camera`（主/子码流路径、凭据已配置标志、外键 → station 与 inference_backend）。
- **连接器域**（`device`，仅配置）：`device_connector`（类型 = `hikvision_isapi` / `board_card`、连接参数、健康状态）、`device_connector_point`（方向 in/out、点位号、语义标签如"工件到位"/"停线联锁"、外键 → connector 与 station）。模板按语义标签引用点位，不写死设备地址。**工位可以没有任何连接器。**
- **模板域**（`template`）：`template_sop`、`template_version`（不可变，含 Excel 导入引用、actions.json、vlm_prompts、运行参数、顺序性声明、sha256、发布者与发布时刻）、`template_draft`（可编辑，含 `revision` 乐观锁列）、`template_station_binding`（`desired_version` / `reported_version`，后者由推理机上报，§5.3）。
- **训练数据域**（`dataset`）：`dataset_training_dataset`、`dataset_member`（**数据集内的视频**：MinIO key、来源、大小、sha256、时长、编码）、`dataset_annotation`（动作时间段标注）、`dataset_usage_check`（DDM/VLM 用途、状态、原因）、`dataset_artifact`（生成的 DDM `annotation.json` 等派生制品及摘要）。上传、标注、用途检查、转换和训练是不同状态，不合并成一个"成功"。
- **上报镜像域**（`monitor`）：`monitor_sop_instance`（起止、闭合原因、边界信号来源、上报时刻）、`monitor_decision`（hypertable，判定结果 + 原因码 + 模板版本 + 推理机自报模型标识）、`monitor_observation`（hypertable，动作编号与外部信号同表）、`monitor_stream_health`（hypertable，含时间锚定偏移）。全部按事件 id 幂等 upsert，权威在推理机本地。
- **违规域**：`alert_violation`（kind、锁存标志、来源推理机）、`alert_disposal`（action、执行状态、幂等键）、`evidence_evidence`（MinIO key、类型）、`evidence_review`（复核结论、复核人）。违规与处置的执行权威在推理机，中心表是归档与复核载体。
- **基础域**（`auth`）：`auth_user`（含停用状态）、`auth_role`、`auth_permission`、`auth_role_permission`、`auth_session`。**不设 `auth_audit_log`**（§5.15）。
- **作业域**（`job`）：`job_application_job`（异步任务权威与 outbox；ADR-0004）。

**判定结果表归 `monitor` 而非独立的 judgment 模块**：判定核心是推理机内的纯函数，永久无表。中心侧只存上报镜像，命名与所有权都归 `monitor`，表前缀规则与纯函数要求因此不再互锁。

### 推理机（SQLite，每机一份）

`local_config`（已确认的设备配置与凭据密文）、`local_template_version`（已确认模板版本 + sha256）、`local_sop_instance`、`local_decision`、`local_violation`（锁存）、`local_disposal`（含幂等键与执行结果）、`local_report_queue`（待上报，至少一次）、`local_evidence_queue`（待上传）。

**关键不变量**：违规一经确认即锁存，不因后续补做或处置失败而消失；锁存发生在推理机本地，不依赖中心可达。

## 八、开发路线

与最初五阶段的**两处最大差异**：DDM 训练从阶段三提前到阶段一（没有 DDM 权重推理服务起不来，§2.7）；判定逻辑从中心移入推理机（§5.11 的判定核心），故基座改造与判定核心同属阶段 0。

### 阶段 0（4090 到位前，全部用真实数据可验证）

1. `git subtree` 接入 NVIDIA 仓库；根 `CONTEXT.md` + 首批 ADR（0005~0009）。
2. **基座契约测试 + 自有回归测试**（§5.9）——§2.2 的返工用例是第一个要通过的。
3. **判定核心**（`apps/edge-runtime/`，纯标准库纯函数）：序列比对、声明式边界、有效性门、三值判定、14 原因码、顺序型跳号即报。单元测试覆盖安全不变量。
4. **基座两处改造 + 最小 hook**（§5.11）：pipeline `on_message` 输出流健康事件、处置扩成 5 种动作。维护为可重放补丁；纯 CPU 可验证的部分立即验证。
5. 中心数据模型与迁移。
6. 鉴权 + 自定义权限 + 诊断日志基线。
7. 设备配置 CRUD（推理主机 / 工位 / 相机 / 推理后端绑定）。
8. Excel 解析校验 + `actions.json` / `vlm_prompts.txt` 生成（用真实 Excel 验证，严配基座正则）。
9. 视频逐个上传（预签名直传 MinIO）+ 数据集登记 + **原样复用基座标注 UI 并在网关补鉴权** + DDM/VLM 用途检查 + 由标注生成 DDM `annotation.json`。
10. mediamtx 预览与录像 + 浏览器直连多路视频（**首验海康子码流 `has_b_frames`**，并验证目标大屏并发解码与网络容量，§5.5）。
11. 推理机 supervisor 骨架：本地状态、模板拉取与本地落盘、上报队列与对账、时间锚定、证据切片（真实 RTSP 验证断流检出与重连后重新锚定）。

## 九、验收门禁

**正确性**：

- **返工序列不得误报**（§2.2 的 `1,2,3,2,4,5` 判通过）——这是本产品与基座原样行为的分水岭；
- 注入断流 / 丢帧 / 推理超时 / 时间戳跳变 / 点位断线 / 重连后时间轴归零时，系统不得输出错误的不通过；
- **闭合前有效性门生效**：断流期间触发空闲超时闭合时输出不可判定 + `STREAM_LOST`，不进入漏步集合比对；
- 漏步在实例闭合时立即报出（不等下一遍）；顺序型模板跳号即报；
- 每个不通过可追溯到模板版本、推理机自报模型标识、观测与证据；
- 模板切换期间旧实例不污染新版本；
- **未配置任何连接器的工位与配置了连接器的工位走同一套判定代码路径**（无 `if 配了连接器` 分支）。

**自治性**：切断中心—推理机网络后，判定、违规锁存、处置（含写输出点位）、证据切片、预览全部继续；恢复后上报对账幂等，处置不重复执行，证据不丢失；不兼容版本显式告警拒绝接入，不静默降级。

**性能**：按 §5.6 两类起点分别报告 p50/p95/p99、最大值和超预算计数；每个成功实时结果必须 ≤ 500 ms，测试窗口内超预算结果为零。拆分 DeepStream/chunk、DDM、VLM、判定核心、supervisor、上报、中心 SSE 和 Web 渲染耗时。长流 chunk delay 不持续增长；预览不得反压判定；**外部信号到判定的延迟**单独报（轮询模式下须报轮询周期）。**每推理后端的常驻显存开销单列**（§5.10 容量公式的一项）。

**稳定性**：先 72h 再 7 天；记录 RSS、显存、句柄、队列深度、延迟趋势、时间锚定偏移漂移、**SQLite 本地状态增长与录像磁盘水位**（§5.5 容量公式）；覆盖容器重启、宿主重启、磁盘不足、相机重启、连接器掉线恢复、中心离线与恢复。

**安全**：所有管理 API 认证授权（含反代的标注 UI 与训练微服务）；模板版本 sha256 校验且推理机上报实际生效值；推理服务离线启动不访问公网；**凭据不出现在中心的任何导出物、日志或 API 响应中**（§5.12）；**写输出点位的动作全部产生诊断日志事件**（物理联锁属高影响操作），并记录操作人与目标点位。
