# 判定在推理机内完成，中心不在实时路径上

三值判定、SOP 实例边界与安全不变量都在推理机上、由本机 supervisor 进程实现。中心是管理面与聚合面：下发配置、接收上报、提供看板与复核。中心不订阅推理服务 SSE，不做判定。

**判定在推理机上，但不在基座进程内。** supervisor 消费本机推理服务的 `/v1/chat/completions` SSE 流并在自己的进程里判定；基座自带的 checker 用它既有的 `DISABLE_SOP_CHECKER=true` 关掉，不打补丁替换。判定核心是 `apps/edge-runtime/` 内的纯函数模块，由 supervisor 调用。

## 两条独立理由

**一、有效性所需的第一手信号在推理机。** 区分"没做"与"没看到"需要流健康：`on_message` 回调直接观测 `INVALID`（source error）、`PLAYING`（delivering）与 EOS，当前 chunk 算法的后处理直接观测其消费的 PTS 是否回退。源元件内部重连没有独立总线消息，因此登记补丁把 callback 事实归一进 SSE，并在 uniform/DDM 后处理发现实际 PTS 回退时重置对应分块状态并重新锚定 `first_timestamp`；supervisor 由后续 chunk 的 `source_anchor` 变化识别时间轴归零。把判定放在中心，中心就只能靠独立 RTSP 探活二次猜测这些第一手事实——那是两套互相不一致的实现，而正确答案在推理机。

**二、中心不得是实时防错的单点故障。** 原设计把订阅与判定放在中心的单一 ingest 进程（`replicas=1`），中心一挂，全部工位同时失去实时防错，而物理联锁信号还要绕中心跑一趟。工厂产线不接受这种拓扑。判定与处置在推理机本地闭环后，中心离线只影响看板与复核。

## Considered Options

- **中心 ingest 订阅 SSE + 中心 judgment 模块**（原方案）：模块边界干净，但同时踩上面两条——第一手信号拿不到，且中心成为全厂单点。
- **中心判定 + 边缘探活上报健康**：把流健康从推理机传到中心再判定。信号绕一圈，延迟与失真都增加，且中心单点问题不变。
- **判定在基座进程内（替换基座 checker 调用点）**：判定核心补进 `ds_sop_process.py` 的 checker 调用点。被否决，三条实测理由：① 那是控制流替换而非追加输出，与本仓库对 `missing_number_detector` 拒绝打补丁的理由同构（[ADR-0007](0007-base-is-the-trunk-not-a-dependency.md)）；② 承载它的循环是 `_vlm_response_queue.get(block=True)`（`ds_sop_process.py:715`，无超时），判定核心只能被"chunk 到达"唤醒，而空闲超时要检出的恰是"chunk 不再到达"——要让计时器能响必须连该循环一起补，成为对同一方法的第二次侵入，等于复刻 §2.3"当班最后一遍永不报"的缺陷；③ 无效率收益：判定结果无论如何都要跨 SSE 才能到 supervisor（锁存、证据、上报、本地 SQLite 都在那里），两条路径下结果到达 supervisor 的时刻相同，差别只是约 30 µs 的判定计算落在这一跳之前还是之后。
- **判定在推理机的 supervisor 进程内（采纳）**：判定与信号源、与处置执行点同机，且不进入基座控制流。基座 checker 用既有环境变量关闭，不新增补丁。

## Consequences

- 流租约不再需要。租约存在的唯一理由是"中心多个进程可能重复订阅同一路相机、重复启 DeepStream pipeline 重复占显存"。本机 supervisor 驱动本机 pipeline 后，"每路流有且仅有一个拥有者"退化为本机进程管理问题。原 ADR-0001 因此作废并删除。
- 判定核心不再受"必须能在基座容器解释器内运行"约束，因为它跑在 supervisor 里。**但只依赖标准库这条规则保留**：成本近零，且它保证判定核心可纯 CPU 单元测试，与基座那四个模块同级。规则的理由从"运行环境强制"改为"可测试性与可移植性"。`vendor/` 内登记补丁调用的健康 hook 仍必须只依赖标准库，因为它确实运行在基座容器内；同补丁的 PTS 回退处理只使用基座已有的分块状态。
- 判定核心不与基座 pipeline 争 GIL。基座每路流约 10 个线程、checker 池 `max_workers=1`（`ds_sop_process.py:666`）、各级队列无界；判定放在独立进程可避免我们的负载在他人进程内造成积压，且积压表现为我们自己进程的 SSE 读取滞后，指标与处置都在我们掌握内。
- 中心的 `monitor` 模块是上报镜像而非判定权威，行覆盖来自推理机的幂等 upsert。判定权威、违规锁存权威与处置执行权威都在推理机本地 SQLite。
- 推理机需要本地持久化、对账协议与版本握手。这是消除单点故障的必要成本。
- 每台推理机都要能独立排障。诊断日志与指标必须在本机可读，不能只在中心聚合后才可见。
