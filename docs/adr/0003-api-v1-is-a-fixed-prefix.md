# `/api/v1` 是固定前缀，不是版本轴

中心后台控制面路径固定以 `/api/v1` 开头，但**该前缀不是版本轴**：不会出现 `/api/v2`。契约只做向后兼容演进（加可选字段、加端点），破坏性变更走全客户端协同发布，而不是并行维护两个版本。

## Consequences

- OpenAPI 由 FastAPI 代码生成，导出到 `packages/contracts/openapi.json`，CI 校验重新生成后工作区干净。契约兼容性检查必须能让破坏性变更失败——删除路径或字段、新增必填字段、收窄类型都是失败项，因为没有 v2 可供旧客户端退守。
- **响应枚举加值不是破坏性变更，删值与改语义是。** 判定原因码集合会增长（[`judgment-and-boundary.md`](../design/mechanisms/judgment-and-boundary.md) §5.2），而没有 v2 供旧前端退守，故代价转移到客户端：所有客户端必须对未知枚举值有兜底渲染——原因码显示原始码 + 通用提示，不显示空白、不显示"未知错误"、不丢弃该条记录。兜底不成立时，这条豁免也就不成立。请求枚举加值同理可容忍，因为旧客户端不会发送新值。
- 单工厂内网、前后端同一交付物，协同发布成本低；并行版本的长期维护成本远高于收益。
- 推理机上的边缘运行时与可下载部署包是可能非同步升级的客户端。它们不靠 URL 版本兼容；每条机器契约在行为演进时必须有足够的显式兼容协商，不兼容即拒绝并显式告警，不静默降级。配置束采用[单一当前模型与能力要求](../design/mechanisms/machine-contract-evolution.md)：常规字段演进不新增并行 generation；影响行为的字段必须绑定 `required_capabilities`，旧 Edge 不支持时直接拒绝。配置束的 `contract_version` 不是覆盖全部 Center↔Edge 接口的软件版本握手。
