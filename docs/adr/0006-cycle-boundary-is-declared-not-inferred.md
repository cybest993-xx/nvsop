# SOP 实例边界由模板声明，不由动作序列推断

基座 `MissingNumberDetector` 用两条启发式猜周期边界：见重复号且已见 `N×0.6` 个动作，或低号 ≤`N×0.3` 出现在高号 ≥`N×0.8` 之后（`missing_number_detector.py:149-166`）。我们保留它的序列比对逻辑，**替换边界来源**为模板声明的信号。

## 实测依据

5 步 SOP，操作员做 1,2,3 后返工重做 2，再继续 4,5——一遍完全合规的作业：

```
输入(1)  missing=[]        输入(2)  missing=[]        输入(3)  missing=[]
输入(2)  missing=[4,5]  ← 返工触发周期边界，seen_in_cycle 被清空
输入(4)  missing=[]        输入(5)  missing=[]
终帧     final_missing=[1,3]
```

一遍合规作业被判两次不合规。返工在工厂是常态，该启发式在产线上不可用。

此外，`cycle_completed=True` 的条件是 `len(seen_in_cycle) == N`，漏一步永远凑不满；`missing` 只在下一周期边界或流结束（`keep_alive=False`）时产出。对 7×24 常驻流，当班最后一遍的漏步永远不报。

## 决定

序列比对与边界求解在 `apps/edge-runtime/` **自己实现**，不打补丁改造基座的 `MissingNumberDetector`（理由见 [ADR-0007](0007-base-is-the-trunk-not-a-dependency.md)：边界判断与序列比对交织在 `process_number` 同一方法内，换边界来源必须整体覆写）。行为定义如下：

- **开实例**：模板声明的开始信号首次满足（动作编号，或已配置连接器的外部信号点位）。
- **闭实例**（任一先到）：模板声明的结束信号满足；动作集合齐全（保留基座 `cycle_completed` 的语义：`len(seen) == N`）；空闲超时（该工位生效的空闲时限，用推理机主机单调钟度量；生效值属于工位，模板版本只给默认值，见 solution-and-roadmap.md §5.3）。
- **闭合前强制过有效性门**：流健康或推理可达性任一不满足，闭合为不可判定，不进入漏步集合比对。
- **顺序型模板跳号即报漏步**，闭合时的集合比对退为兜底。**首版每个步骤都必做，不支持可跳过步骤**：基座 `actions_can_be_skipped` 的实测语义是"该动作不属于本 SOP"（从期望集合剔除且丢弃其观测），表达不了产品要的"可选但计入顺序"。见 solution-and-roadmap.md §5.1。
- **不实现的**：基座那两条周期边界启发式，以及驱动它们的三个阈值。

## Consequences

- 返工不再误报：边界不由重复号触发，`seen_in_cycle` 不在实例中途被清空。§2.2 的用例固化为最高优先级回归测试。
- "当班最后一遍永不报"在源头消失：空闲时限就是那个缺失的时间信号。
- 我们拥有这段序列比对逻辑的维护责任。这不是净增负担：边界求解、有效性门、三值判定本来就要我们写，而它们与序列比对共享同一份状态。
- 基座三个阈值（0.6/0.3/0.8）不再有对应实现。它们在部署态本来也不可配——`ChatCompletionRequest` 无此字段，`ds_sop_process.py:735` 从 chunk dict 读，而全仓无任何代码往 chunk 写这三个键。
- 契约测试需一条新断言：我们的实现与基座在**合规序列**上结论一致（不含返工与漏步时机——那正是我们故意不同的地方）。
- 空闲超时必须用主机单调钟，不能用 chunk 时间戳：chunk 时间戳无法度量"chunk 不再到达"。断流后计时器触发而直接算漏步会输出错误的不通过，有效性门为拦住这条路径而存在。
- 单通道感知的固有局限随之明确，见 [ADR-0009](0009-single-channel-perception-limit.md)。
